# Naomi's Coffee Club App — Version Upgrade Plan

Prepared September 14, 2026, from the project at `C:\Users\amakh\Cafe\naomis_app`. Scope: the app's own version number, plus the Android and iOS build toolchain versions (Gradle, AGP, Kotlin, iOS deployment target).

## What the project looks like today

This is a Flutter app ("Naomi's Coffee Club — companion app") with a working navigation skeleton and theme, but per its own README the real screen content (menu data, events, location/hours, about text) hasn't been built yet — it's an early-stage skeleton, not a finished app. There's no git repository yet, so there's no version history to lean on.

The Android project was generated by a fairly recent Flutter SDK: the Gradle files use Kotlin DSL (`build.gradle.kts`), Gradle 9.1.0, Android Gradle Plugin (AGP) 9.0.1, and Kotlin 2.3.20. A debug build has already been run once — the merged manifest shows `minSdkVersion 24`, `targetSdkVersion 36`, `versionCode 1`, `versionName 0.1.0`, all pulled automatically from the installed Flutter SDK and from `pubspec.yaml`. The iOS project targets iOS 13.0 and uses Swift Package Manager (no CocoaPods `Podfile` exists, which is expected for a project this new).

None of that is "broken," but checking current releases (as of September 2026) against what's pinned in the project shows the Android toolchain has fallen a few releases behind, and the app's version number has a small gap that's worth closing before it causes a real inconsistency.

Important dependency: AGP 9.4.0 requires Gradle 9.6.0 or newer, so Gradle has to be upgraded *before* (or together with) AGP — bumping AGP alone against the current Gradle 9.1.0 wrapper will fail.

`minSdkVersion`, `targetSdkVersion`, and the NDK version aren't hand-pinned anywhere in this project — they're read from the installed Flutter SDK (`flutter.minSdkVersion` etc. in `app/build.gradle.kts`). That's good news: upgrading the Flutter SDK itself will carry those forward automatically, with nothing to edit by hand.

## The app version number

`pubspec.yaml` currently has `version: 0.1.0`, with no `+buildNumber` suffix. That resolves fine on Android (the build tool defaults the missing build number to `versionCode 1`), but the iOS build config (`ios/Flutter/Generated.xcconfig`) shows `FLUTTER_BUILD_NUMBER=0.1.0` — it inherited the full version string instead of defaulting to `1` the way Android did. That's a real cross-platform inconsistency: iOS's `CFBundleVersion` (the build number Apple uses to distinguish builds of the same marketing version) ends up as `0.1.0` instead of a clean incrementing integer.

Given the README shows real screen content still isn't built, staying in the `0.x` range is the semantically correct choice — jumping to `1.0.0` now would overstate what's done. What should change is making the build number explicit: `version: 0.1.0+1`. That removes the platform inconsistency and gives you a real counter to increment on every build you ship to a device, TestFlight, or Play's internal track, independent of the marketing version.

## Step-by-step upgrade procedure

Run these on the machine with the Flutter SDK installed (`C:\Users\amakh\develop\flutter`), from the project folder.

1. **Snapshot the current state.** There's no git repo yet — run `git init && git add -A && git commit -m "Pre-upgrade snapshot"` so you have something to diff against and roll back to if a step goes wrong.
2. **Set the explicit build number.** In `pubspec.yaml`, change `version: 0.1.0` to `version: 0.1.0+1`.
3. **Upgrade the Flutter SDK.** Run `flutter upgrade` (make sure you're on the `stable` channel first: `flutter channel stable`). This should bring you from ~3.44.x to 3.47.2. Confirm with `flutter --version` and `flutter doctor`.
4. **Refresh dependencies against the new SDK.** Run `flutter pub get` so `pubspec.lock` is regenerated against the upgraded SDK.
5. **Bump the Gradle wrapper.** From the `android/` folder, run `./gradlew wrapper --gradle-version 9.7.1` (or hand-edit `android/gradle/wrapper/gradle-wrapper.properties`, changing the `distributionUrl` to point at `gradle-9.7.1-all.zip`). This has to happen before step 6, since AGP 9.4.0 requires Gradle 9.6.0+.
6. **Bump AGP.** In `android/settings.gradle.kts`, change `id("com.android.application") version "9.0.1"` to `version "9.4.0"`.
7. **Bump Kotlin.** In the same file, change `id("org.jetbrains.kotlin.android") version "2.3.20"` to `version "2.4.20"`.
8. **Rebuild and verify Android.** From the project root: `flutter clean`, then `flutter build apk --debug`. Watch the output for AGP/Kotlin deprecation warnings — none are expected across these specific version jumps, but worth a read. Confirm the resulting manifest still shows `versionCode 1`, `versionName 0.1.0`, and whatever `targetSdkVersion` the new Flutter SDK now defaults to.
9. **Verify iOS, if you build on a Mac.** No deployment-target change is needed — 13.0 is still current. Just confirm your installed Xcode version still meets Apple's current minimum for App Store submissions (Apple periodically raises this independently of Flutter), then run `flutter build ios --debug --no-codesign` to make sure the Swift Package Manager–based build still resolves cleanly against the upgraded Flutter SDK.
10. **Commit.** Once both builds succeed, `git add -A && git commit -m "Upgrade Flutter 3.47.2, Gradle 9.7.1, AGP 9.4.0, Kotlin 2.4.20; set explicit build number"`.

## Validation checklist

Before considering the upgrade done: `flutter analyze` runs clean, `flutter test` passes (there's a `test/` folder already), the debug APK installs and launches on a device or emulator, and — if you have Mac access — the iOS build launches in Simulator. Re-check the manifest/`Generated.xcconfig` values afterward to confirm `versionName`/`FLUTTER_BUILD_NAME` show `0.1.0` and the build numbers now agree across platforms as `1`.

## Two things I noticed but left out of scope

You didn't ask about these, but they'll matter before any real release, so flagging them: the Android `applicationId` (and iOS bundle identifier convention) is still the Flutter template placeholder `com.example.naomis_app` — Google Play rejects `com.example.*` namespaces outright, so this needs to become a real reverse-domain ID before a Play Store upload. And since there's no git history yet, tagging each version bump (`git tag v0.1.0+1`) as you go would make it much easier to tell later which build is which. Happy to help with either if useful.
